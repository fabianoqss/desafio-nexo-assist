# Plano 3: API (auth, conversas, rascunhos e console)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Objetivo:** o backend `apps/api` com login por sessão, RBAC, conversas do funcionário (com o ponto de encaixe do agent), rascunhos confirmados por clique humano, console do analista e um cliente resiliente para o serviço de chamados, tudo rodando no Docker Compose ao lado do `ticket-service`.

**Arquitetura:** hexagonal, no mesmo molde do `ticket-service`. `application/` tem os casos de uso e as portas (repositórios, `UnitOfWork`, `Clock`, `TicketGateway`, `AgentTurnRunner`, `ConversationEventBus`, `RateLimiter`, `Metrics`). `adapters/` implementa HTTP (Hono), persistência (Drizzle + Postgres `nexo_api`), o cliente HTTP do serviço de chamados (cockatiel) e os adaptadores em memória. O que o `ticket-service` já tem e a API também precisa (logger, erros, handler de erro, log de requisição, URL do banco) sai para `packages/server-kit`. O agent Mastra é o Plano 4: aqui ele é só a porta `AgentTurnRunner`, com um adaptador "assistente indisponível" que o Plano 4 reaproveita como fallback do teto de gasto.

**Stack:** Node 26, Hono 4 + `@hono/node-server` (`streamSSE`), Zod 4, Drizzle ORM + drizzle-kit + `pg`, pino, cockatiel 4 (timeout, retry e circuit breaker), esbuild, Vitest + `@testcontainers/postgresql`, Docker Compose com Postgres 18.

**Spec:** `docs/design/design-doc.md` (seções 2, 3, 5 "Turn flow", "Safety by design", "Handoff triggers" e "Unreliable ticket service", 6 `nexo_api`, 7, 9, 10 e 11)

## Global Constraints

- Tudo dos Planos 1 e 2 continua valendo: Node `>=26`, pnpm `12.x`, TypeScript estrito, ESM, sem `any`, sem comentários, dependências com versão exata, `pnpm audit --audit-level=high` sem achados, nunca exceção em `minimumReleaseAge` (se a última versão tiver menos de 1 dia, fixe a anterior).
- Pastas: DTOs em `request/` e `response/`; portas em `application/ports/`; adaptadores em `adapters/<tipo>/`. Testes espelham `src/` em `test/`.
- Toda regra de negócio vem de `@nexo/domain`; a API não reimplementa prioridade, prazo, vencido, reabertura nem transições de conversa.
- **A identidade nunca vem do corpo da requisição.** O usuário vem sempre da sessão; o `actorId` enviado ao serviço de chamados é o da sessão.
- UUIDs de usuário trafegam em minúsculas (`LowercaseUuidSchema`); textos livres usam `boundedText` (sem U+0000). Limites: `content` de mensagem 1–4000; `password` 1–200; `email` até 254.
- Datas em JSON como ISO 8601 UTC. `overdue` é sempre calculado na leitura.
- Sessão: token aleatório de 32 bytes (`base64url`), só o SHA-256 vai para o banco; cookie `__Host-nexo_session`, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`; validade absoluta de `SESSION_TTL_HOURS` (padrão `12`).
- Proteção CSRF: toda requisição com método diferente de `GET`/`HEAD`/`OPTIONS` exige `Origin` igual a `WEB_ORIGIN` (senão 403) e, quando tem corpo, `Content-Type: application/json` (senão 415 `UNSUPPORTED_MEDIA_TYPE`).
- CORS só para `WEB_ORIGIN`, com `credentials: true`.
- Rate limits (porta `RateLimiter`, adaptador em memória, janela fixa): login 10/min por IP; mensagens 20/min por usuário; `/public/stats` 60/min por IP. Estourou: 429 `RATE_LIMITED` com header `Retry-After`. IP do cliente: `X-Forwarded-For` só quando `TRUST_PROXY=true`, senão o endereço do socket.
- Logs JSON sem corpo, conteúdo de mensagem nem dados pessoais: só ids (`requestId`, `userId`, `conversationId`), método, rota, status e duração. Erros inesperados via `describeError`.
- Limite de mensagens: 30 mensagens do funcionário por conversa (`MAX_EMPLOYEE_MESSAGES`).
- Banco `nexo_api` com papel dono (`nexo_api_owner`, migrações) e papel de runtime (`nexo_api_app`, só `SELECT`, `INSERT`, `UPDATE` e `DELETE` apenas em `sessions`), no mesmo padrão do `nexo_tickets`.
- Métricas: toda funcionalidade registra suas métricas pela porta `Metrics` (nomes na Task 4). O adaptador Prometheus é do Plano 6; aqui o app usa um adaptador que não exporta nada, e os testes usam um que grava em memória.
- Cobertura mínima: `apps/api/src` 85% linhas e 80% branches (sem `main.ts`, `migrate.ts` e `seed/run-seed.ts`); `packages/server-kit/src` 90% linhas.

## Contrato HTTP da API

Erros no formato `{ "error": { "code", "message" } }` do `@nexo/contracts`. Sessão obrigatória em tudo, exceto `/health`, `/ready`, `/auth/login` e `/public/stats`.

| Método e rota                              | Quem        | Faz                                                                                           | Sucesso |
| ------------------------------------------ | ----------- | --------------------------------------------------------------------------------------------- | ------- |
| `POST /auth/login`                         | público     | `{ email, password }`; qualquer senha não vazia para um e-mail do seed; grava sessão e cookie | 200     |
| `POST /auth/logout`                        | logado      | Apaga a sessão e expira o cookie                                                              | 204     |
| `GET /auth/me`                             | logado      | `UserResponse`                                                                                | 200     |
| `GET /public/stats`                        | público     | `PublicStatsResponse` (cache de 60 s)                                                         | 200     |
| `GET /conversations/current`               | funcionário | Conversa aberta (cria uma `WITH_AGENT` se não houver), mensagens e rascunhos pendentes        | 200     |
| `POST /conversations/:id/messages`         | funcionário | Grava a mensagem e responde em SSE (eventos da Task 3); só chama o agent se `WITH_AGENT`      | 200     |
| `POST /conversations/:id/handoff`          | funcionário | Pede um analista (`EMPLOYEE_REQUEST` ou `MESSAGE_LIMIT`)                                      | 200     |
| `GET /conversations/:id/events`            | funcionário | SSE com mensagens do analista e mudanças de status da própria conversa                        | 200     |
| `POST /drafts/:id/confirm`                 | funcionário | Executa o rascunho no serviço de chamados                                                     | 200     |
| `POST /drafts/:id/cancel`                  | funcionário | Cancela o rascunho                                                                            | 200     |
| `GET /console/conversations?filter=`       | analista    | Lista (`ALL`, `FOR_YOU`, `WITH_AGENT`, `MINE`)                                                | 200     |
| `GET /console/conversations/:id`           | analista    | Conversa com mensagens e resumo do handoff                                                    | 200     |
| `GET /console/events`                      | analista    | SSE com mudanças em qualquer conversa                                                         | 200     |
| `POST /console/conversations/:id/assume`   | analista    | `WAITING_ANALYST` → `WITH_ANALYST`, atribui a si                                              | 200     |
| `POST /console/conversations/:id/return`   | analista    | `WITH_ANALYST` (sua) → `WITH_AGENT`                                                           | 200     |
| `POST /console/conversations/:id/close`    | analista    | → `CLOSED`                                                                                    | 200     |
| `POST /console/conversations/:id/messages` | analista    | Responde ao funcionário (só se `WITH_ANALYST` e atribuída a ele)                              | 201     |
| `GET /console/employees/:id/tickets`       | analista    | Chamados do funcionário via serviço de chamados                                               | 200     |

Regras de acesso: funcionário só enxerga as próprias conversas e rascunhos. Id de conversa ou rascunho de outra pessoa dá **404**, igual a id inexistente. Papel errado dá **403**.

| Código novo (`error.code`)    | HTTP | Quando                                                            |
| ----------------------------- | ---- | ----------------------------------------------------------------- |
| `INVALID_CREDENTIALS`         | 401  | E-mail fora do seed ou senha vazia (mesma mensagem para os dois)  |
| `UNSUPPORTED_MEDIA_TYPE`      | 415  | Corpo sem `Content-Type: application/json`                        |
| `RATE_LIMITED`                | 429  | Limite de requisições estourado                                   |
| `MESSAGE_LIMIT_REACHED`       | 409  | 30 mensagens do funcionário na conversa                           |
| `CONVERSATION_STATE_CONFLICT` | 409  | Ação inválida para o status atual, ou conversa assumida por outro |
| `DRAFT_NOT_PENDING`           | 409  | Rascunho já confirmado ou cancelado                               |
| `TICKET_SERVICE_UNAVAILABLE`  | 503  | Serviço de chamados fora após os retries, ou circuito aberto      |

## Review Focus

1. **Funcionário mexendo no que não é dele** (Ana confirmando o rascunho de uma conversa do Bruno, ou lendo `/conversations/<id do Bruno>/events`): 404, nunca o dado nem a ação. Testes nas Tasks 8 e 9.
2. **Duplo clique em "Confirmar", ou reenvio após timeout:** um único chamado é criado (a chave de idempotência é derivada do id do rascunho) e o rascunho termina `CONFIRMED` com o mesmo `ticketId`. Teste na Task 9.
3. **Serviço de chamados fora do ar durante a confirmação:** depois dos retries a resposta é 503 `TICKET_SERVICE_UNAVAILABLE`, o rascunho continua `PENDING` e, com o circuito aberto, as próximas falham na hora, sem esperar timeout. Testes nas Tasks 7 e 9.
4. **Dois analistas clicando em "Assumir" ao mesmo tempo:** um recebe 200 e o outro 409 `CONVERSATION_STATE_CONFLICT`; a conversa fica atribuída a um só. Teste na Task 10.
5. **Página de outro site postando com o cookie da vítima** (`Origin` diferente): 403 antes de qualquer efeito; e um script tentando senhas no login recebe 429. Testes na Task 6.
